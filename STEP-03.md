# Шаг 3: три виртуальные машины для Kubernetes

Архив дополняет существующий проект `devops-diploma-infra`: добавляет четыре файла
Terraform, два Bash-скрипта и эту инструкцию. Выполняйте команды из корня проекта.

## Состав стенда

| ВМ | Зона | CPU | RAM | HDD | Прерываемая | Публичный IP |
|---|---|---|---|---|---|---|
| control-plane | ru-central1-a | 2 vCPU, 20% | 2 ГиБ | 10 ГиБ | Нет | Статический |
| worker-1 | ru-central1-b | 2 vCPU, 20% | 2 ГиБ | 10 ГиБ | Да | Статический |
| worker-2 | ru-central1-d | 2 vCPU, 20% | 4 ГиБ | 10 ГиБ | Да | Динамический |

Платформа: Intel Ice Lake (`standard-v3`). Образ Ubuntu 24.04 закреплён на
`fd8041m4h84kooeovknf`, проверенном пользователем 1 ноября 2026 года:
`min_disk_size: 10737418240` = 10 ГиБ. Зоны `a`, `b`, `d` проверены через `yc`,
статус каждой — `UP`. Внутренние адреса: `10.20.10.10`, `10.20.20.10`, `10.20.30.10`.

Один worker получает 4 ГиБ под мониторинг. HDD 10 ГиБ — экономный начальный размер,
не обещание достаточности для произвольного числа образов и длительного хранения
метрик. После установки мониторинга проверим свободное место, ограничим объём и
срок хранения метрик; при необходимости увеличим диск через Terraform.

Статические IP сохраняют адрес API и адрес будущего HTTP ingress при остановке
ВМ. Это учебный кластер с одним control plane; размещение в нескольких зонах не
делает control plane отказоустойчивым. Прерываемые worker могут останавливаться,
поэтому перед проверкой работы или защитой их потребуется запускать.

## Доступ

- Между узлами одной группы разрешён внутренний трафик кластера.
- SSH/22 — только с IPv4-адреса администратора (`/32`).
- API Kubernetes/6443 — из интернета только на control plane; после установки
  kubeadm API будет использовать TLS и аутентификацию. Для CI/CD позже создадим
  отдельные credentials с правами деплоя приложения.
- HTTP/80 — из интернета на worker. Контроллер ingress установим следующим этапом.
- Исходящие соединения разрешены для установки пакетов и загрузки образов.
- Сервисный аккаунт Terraform к ВМ не прикрепляется.
- Вход по SSH: `ubuntu`, ключи; парольный вход и root-вход выключены через cloud-init.

Скрипт определяет публичный IPv4 через api.ipify.org. При VPN или раздельной
маршрутизации убедитесь, что это тот IP, с которого пойдёт SSH в Yandex Cloud.
Если нужен другой адрес, задайте его явно:

```bash
DIPLOMA_ADMIN_IP=203.0.113.10 bash scripts/prepare-vms.sh
```

`203.0.113.10` — пример; замените реальным публичным IPv4. После изменения IP
обновите входные данные тем же скриптом и примените план изменения группы безопасности.

## Подготовка

Распакуйте архив в `~/netology`, затем:

```bash
cd ~/netology/devops-diploma-infra
bash scripts/prepare-vms.sh
```

Скрипт создаёт отдельную ключевую пару `.secrets/diploma-ssh` (без парольной фразы,
для автоматического подключения Ansible), сохраняет существующий ключ при повторном
запуске, создаёт/обновляет `terraform/main/local.auto.tfvars.json` с публичным ключом
и разрешённым адресом SSH. Оба пути уже исключены из Git исходным `.gitignore`.
Закрытый ключ в конфигурацию Terraform не копируется.

Файл `.secrets/terraform-key.json` из предыдущего шага — другой ключ; он используется
для API облака и не заменяет SSH-ключ.

В том же терминале должны оставаться переменные окружения из шага 2. При новой
сессии повторите экспорты из `STEP-02.md`, без повторного создания ключа аккаунта.

## Проверка плана

```bash
terraform -chdir=terraform/main fmt
terraform -chdir=terraform/main validate
terraform -chdir=terraform/main plan
```

Новых провайдеров нет, повторный `init` не требуется, если предыдущий этап в этой
папке успешно инициализирован. Для уже созданных сети, подсетей и реестра ожидается:

```text
Plan: 8 to add, 0 to change, 0 to destroy.
```

Восемь ресурсов: три ВМ, два статических IP и три группы безопасности. Три диска
создаются внутри ресурсов ВМ и не увеличивают число ресурсов Terraform в плане.
В плане проверьте `cores = 2`, `core_fraction = 20`, `memory = 2/2/4`,
`type = "network-hdd"`, `size = 10`, worker `preemptible = true`.

## Применение и проверка SSH

После проверки плана:

```bash
terraform -chdir=terraform/main apply
terraform -chdir=terraform/main output ssh_commands
```

При запросе подтверждения `apply` введите `yes`. Дождитесь завершения cloud-init
перед установкой Kubernetes. Скопируйте команду SSH для control plane из Outputs.
Отпечаток ключа хоста при первом соединении проверьте по доступному доверенному
каналу консоли ВМ, затем подтвердите соединение. Не выключайте проверку host keys.

На каждой ВМ проверим:

```bash
sudo cloud-init status --wait
hostname
free -h
df -h /
```

Пока это три Ubuntu-сервера. Kubernetes установим Ansible следующим этапом.
Сохраните скриншот окончания `apply`, `terraform output nodes` и повторного
`terraform plan` с `No changes`.

## Остановка и запуск

Из корня проекта, с рабочими backend credentials и пользовательским профилем yc:

```bash
bash scripts/nodes.sh stop
bash scripts/nodes.sh status
```

Запуск:

```bash
bash scripts/nodes.sh start
terraform -chdir=terraform/main apply -refresh-only
terraform -chdir=terraform/main output ssh_commands
```

Режим `-refresh-only` обновляет сведения в state после смены динамического IP
worker-2; он не создаёт новые ресурсы. Проверьте показанный план и подтвердите
обновление. При первом создании ВМ запускаются автоматически.

## Проверки этого архива

Локально проверены HCL и синтаксис Bash; Terraform `validate`, облачный `plan`,
создание ВМ и SSH проверяются в окружении пользователя. Никакие реальные ключи,
state или файлы локальных переменных в архив не включены.
