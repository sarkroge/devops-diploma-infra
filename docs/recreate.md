# Подготовка проверки terraform destroy/apply

Полный цикл ещё не выполнен. Сначала проверяется автозапуск по [инструкции эксплуатации](operations.md),
затем собирается конкретный план удаления и восстановления.

## Что затронет основной destroy

Основная конфигурация включает три ВМ с boot-дисками, два статических адреса,
security groups, сеть/подсети и Container Registry. Bootstrap сохраняется.

- Данные local PV на boot-диске worker-2 будут потеряны при удалении ВМ.
- Выданные заново публичные IP могут отличаться. Потребуются новые ссылки,
  root_url Grafana и APP_URL приложения.
- Новый кластер получит новые сертификаты и токен deployer. KUBE_CONFIG
  приложения потребуется заменить после create-cd-kubeconfig.py.
- Новый реестр получит другой ID. Потребуется обновить YC_REGISTRY_ID приложения
  и повторно опубликовать образ из его исходного Git-тега.
- Удаление непустого Registry требует отдельной подготовки образов/очистки.
  План Terraform сам по себе не подтверждает успешность этой операции.

Инструкция не подменяет проверку destroy/apply запуском остановленных ВМ
и не объявляет переносимость сохранённых токенов между разными кластерами.

## Сначала собрать резервные копии и план, без удаления

Убедитесь, что инфраструктурные Actions завершились и новые push/ручные CI-запуски
на время проверки исключены. Используется единственный state без распределённой
блокировки. Для настоящего destroy предварительно отключается таймер по [инструкции эксплуатации](operations.md).

Из корня infra:

```bash
python3 scripts/prepare-recreate.py
```

Скрипт:

1. Проверяет существующий JSON-ключ Terraform и его service account ID.
2. Читает state bootstrap и main; сохраняет защищённые копии в .secrets/recreate-*.
3. Копирует локальные файлы ключей/доступов и tfvars с правами 0600.
4. Читает список образов Registry.
5. Создаёт plan -destroy в защищённом каталоге; выводит только адреса ресурсов
   и действия. Не выполняет apply/destroy, не удаляет образы.

Для проверки плана достаточно строк Registry images, Planned resource changes и
адресов ресурсов. State, ключи, бинарный plan и каталог резервных копий не отправляются
в публичный Git. Резервная копия state не является копией дисков ВМ или слоёв образов.

Для текущей основной конфигурации ожидается 13 удаляемых ресурсов. Если состав
изменился, ориентироваться нужно на фактические адреса и действия в плане.

## Что проверить перед фактическим циклом

- Сохранены ли исходники и Git-тег приложения, из которого будет собран образ.
- Подготовлено ли сохранение/повторная публикация образов и автоматическая очистка
  реестра для destroy. Пока она не добавлена, готовность к destroy не подтверждена.
- Сохранены ли нужные данные мониторинга или допустимо начать историю заново.
- Отключён ли автозапуск и исключены ли параллельные infrastructure CI-запуски.
- Понятен ли порядок обновления внешних IP, переменных Actions и KUBE_CONFIG.

После разбора плана подготавливается сам цикл с сохранением логов destroy/apply.
Отсутствие ручных действий относится к созданию/удалению ресурсов основной
Terraform-конфигурации; установка Kubernetes, публикация приложения и восстановление
Secrets внешнего CI — следующие отдельные этапы восстановления полного стенда.

## Порядок восстановления после успешного apply

1. Убедиться в No changes основного Terraform.
2. Обновить inventory; при замене ВМ проверить новые SSH host fingerprints.
   Не отключать проверку host keys и не удалять все записи known_hosts.
3. Выполнить Ansible site.yml и install-kubeconfig.py.
4. Обновить YC_REGISTRY_ID; повторно собрать образ из существующего Git-тега
   workflow приложения (ручной workflow_dispatch собирает/публикует, но не запускает CD).
5. Создать imagePullSecret, установить Traefik, развернуть приложение.
6. Восстановить мониторинг; убедиться, что выбран ожидаемый пароль Grafana.
7. Создать deployer kubeconfig заново, заменить KUBE_CONFIG и APP_URL в Actions.
8. Проверить три Ready-узла, приложение, Grafana и healthy targets.
9. Включить ограниченное окно автозапуска снова; обновить ссылки и доказательства.

Новые публичные адреса и пароль передаются преподавателю отдельно после восстановления.
